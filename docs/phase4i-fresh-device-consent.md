# Phase 4I foundation — fresh device consent transition

DeviceSharingActivationService provides an internal transition from a saved preference to a fresh feature-specific consent epoch. It is **unrouted and disabled**: familyguard.device_activation_enabled is literalfalse in application configuration with no environment switch. Only isolated tests override it. No public activation API, Android UI/OS permission, collector or ingestion route was added, and collection_available remainsfalse. This foundation is not native acceptance or permission to enable production collection.

## Transition contract

A caller supplies trusted deviceID/current credentialhash, feature usage/location, and exactly acknowledged:true, expected_version (positive JSONinteger) and feature-specific disclosure_version. Wrong types, omitted fields, stale versions, alternate ownership/content fields and mismatcheddisclosure are rejected without deletion or a grant. The service reauthenticates the current device under its existing credential/stop/revoke/ingestion rowlock before checking the disabled gate, so wrong-family/rotated/revokedcredentials cannot mutate consent.

The prior feature must be an enabled, unrevoked sharing-v1 preference at exactly expected_version. This deliberately requires another explicit user choice beyond saving a preference. The fresh decision uses usage-collection-v1 or location-collection-v1, advances version, sets a new UTC grant timestamp, and atomically purges only the selected device/feature's prior data. Usage purge includes retry watermarks; location and another family's data remain independent. That prevents old totals or queue metadata from being silently relabeled as a new grant. Duplicate confirmation cannot repeat deletion or grant because the sharing-v1 epoch was consumed; replay/stale state409. To create a later epoch, a future reviewed device flow must stop and review the latest preference again.

Response is consent_recorded:true, selectedfeature/newversion/disclosure and collection_available:false. This records a device assertion, not evidence of a physical tap, biometric identity or actual Android OS permission. No parent identity can call a public activation route because none exists. The service cannot independently prove that a bearer holder saw a dialog; a future device integration must provide transparent disclosures, new affirmative controls and required OS permission acceptance. Backend permission fields supplied by a client must never be treated as proof of OS permission.

## Future integration gates

Before exposing this transition, implement and verify real Android disclosure/acknowledgment/cancel/permission-denial/session-recovery behavior, Keystore/process-death and immediate Stop. A future HTTP boundary must use device middleware and a FormRequest (including body/rate limits) without trusting payloadownership. Review OS-specific permissions and current Android background limits. Do not make the literal gate configurable for production just to bypass those prerequisites. Existing saved-preference screens still promise a fresh choice before collection and no data collection is enabled by this milestone.

Internal ingestion services consume only the new epoch/version/time window. Tests demonstrate oldversions/pregrant seconds denied and postgrant minimized totals accepted only inside isolated fixtures; there are still no routed collection endpoints. Stop and revocation retain their immediate purge/version behavior. Actual concurrent confirmer/replay, Stop and revoke are tested with independent PostgreSQL workers using the existing strict uncachedtesting/loopback5433/familyguard_test guard. Those races test finalconsent state, not actual UI/permission behavior or productiondatabase load.

Seven feature cases cover default-off/stringflagdenial/no deletion, ownfeaturepurge/newversion/time/family isolation/replay, strictack/disclosure/version/fieldvalidation, disabled/missing/changedpreferences, crossfamily/rotated/revokedcredentials, oldepoch/pregrant/newingestion behavior, and independentlocation/no publicroute. Three processracecases cover duplicateconfirm exactlyonewinner, Stop and revocation dominating either ordering. Synthetic data only; no development/production database/reset/migration/config enablement or OSsecuritychange.

Phase4 remains incomplete. Native and verified-parent browser/inbox/currentAPI, real OSretention/sharedcache/capacity and hostedCI acceptance remain release gates. Phase5–6 are pending; the automatic Codex loop remains stopped.
