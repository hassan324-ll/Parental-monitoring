# Phase 4J foundation — Android read-only permission readiness review

Activity/Location Sharing Settings now offer Review future permission requirements after a saved preference has been reverified on an authorized device. This is a **read-only readiness review**, not the future collection-consent submission or an Android permission prompt. No server activation call, OS permission request, settings-launch action, new manifest permission, usage/location read or collector is added. The Phase4I backend gate staysfalse/unrouted and collection_available remainsfalse.

The dialog discloses minimized future app identifiers/daily foreground totals or coarse location, corresponding retention, and required type of Android access. An unchecked acknowledgment says this is a readiness check only. Check current access inspects only this app's access; granted still says sharing cannot start. Not-granted and unknown/failed checks assume no grant and collect nothing. Cancel/dismiss never inspects access or sends consent. The dialog scrolls for smaller screens.

AndroidSharingPermissionReader uses this app's UID/package in AppOpsManager.checkOpNoThrow(OPSTR_GET_USAGE_STATS) for usage readiness, and checkSelfPermission(ACCESS_COARSE_LOCATION) for coarse-location readiness. It never queries usage events or location coordinates, accepts results from another package, or launches system permission UI. A missing manager/security/platform failure is unknown. Since this build declares neither usage nor location permissions, readiness is normally not granted. A possible existing system grant is not treated as device/user consent or server activation. OS access can change immediately after inspection; this is a point-in-time check only, not a live permission guarantee.

The pure SharingPermissionReview state machine requires verified authorization, positive saved preference version, fresh acknowledgment and matching current version before inspection. Acknowledgment is consumed by one inspection; result/grant is not persisted. Reopening/reconstruction starts without acknowledgment/results. Changed authorization/preference/busy state cancels the Compose review; pause/stop/disposal cancels it too. This prevents the local review surviving navigation, app backgrounding, credential checks or preference changes. It creates no activation-decision payload and cannot be reused as backend consent.

Eight JVM regressions cover missing authorization/preference, fresh acknowledgment and reopening, not-granted/unknown states, exception redaction, cancellation/pause reset, stale preference/lost authorization, repeated inspection and independent features/reconstruction. JVM tests inject a permission reader: they do not execute Android AppOps/checkSelfPermission, Compose taps/lifecycle events or actual denial prompts. Builds/lint/test APK compilation do not establish native acceptance. Existing nine Keystore instrumentation tests remain separately pending a usable emulator/device.

Next integration still requires an actual native acceptance environment, new explicit activation disclosure/choice separate from this review, OS permission request/denial/revocation flow, recovery/cancellation tests and visible immediate Stop before any collector/ingestion route is enabled. This review must not be relabeled as final consent or activate saved sharing-v1 preferences. Real Firebase/browser/inbox/currentAPI/hostedCI and OSscheduler/sharedcache/retention capacity acceptance remain open. No development/production schema/settings changes or automatic Codex loop restart.
